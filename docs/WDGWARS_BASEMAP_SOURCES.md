# WDGWars native basemap source notes

Reviewed 29 September 2026. The standalone map uses geographic vector data from OpenStreetMap through the fixed HTTPS Overpass endpoint `https://overpass-api.de/api/interpreter`. It does not request raster tiles. These notes describe the basemap, separate from WDGWars territory ownership data.

The app requests one bounded area around the current viewport when the user refreshes or the app schedules a coverage update. Street download zoom must be at least 9. Each dimension is limited to 50 km at zoom 9, 30 km at 10, 16 km at 11, 8 km at 12, and 4 km at 13 or above. Wide views query major roads only; detailed views add local streets and scenery. Only the actual centered subset is claimed as cached coverage. Zooms below 9 use the separate embedded world layer and never issue an Overpass request. Requests are serialized, have a 60-second minimum interval, respect HTTP Retry-After, and never retry inside the basemap client. The UI owns coverage-change scheduling and cooldowns; the basemap layer does not poll GPS or start background requests itself. Overpass receives the bounding box, no WDGWars key or account data. The shared HTTP client verifies TLS, fixes the host, and rejects redirects.

The public service is best effort for occasional personal requests. It can reject or time out requests under load; keep the previous cache and show the error. A broadly deployed application should arrange its own Overpass service rather than depend on the public instance. The operator describes manual use, resource limits, and unsuitable large-scale usage in the [Overpass public-instance guidance](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html). The same guidance explains that exceeding declared memory or time aborts a query; the previous 8 MiB declaration was much lower than the 512 MiB service default. The new 32 MiB budget remains finite and below that default, with the 20-second execution limit unchanged. This reduces a plausible resource-limit cause without asserting that every failure has the same cause. There are no automatic retries or alternate-host failovers in the basemap client.

## What is stored

At zooms 9-10 the query selects motorway, trunk, and primary roads; at 11-12 it also selects secondary and tertiary roads. At 13+ it selects local road/path ways, waterways, closed water areas, parks, and grass/forest landuse. It asks for tags and cropped coordinates, with a 20-second server execution limit, 32 MiB server memory declaration, and separate output quotas. A small central quarter-width/quarter-height box gets the first 160 roads; outer roads get 96 at overview zooms or 80 at detail zooms; detailed scenery gets the final 16 slots. The center is now queried directly and emitted before the wider road selection begins; the default set is reused so full `.r` and `.o` copies are not retained. This ordering keeps remote scenery from consuming the street budget and allows already validated center geometry to survive a later server resource limit. Each group has an `out count` record, so reaching a group quota is reported as partial even when the total local feature capacity is not full. The local response limit is 512 KiB. The native cache holds up to 256 paths, 4096 total vertices, 512 vertices per original way, and a 39-byte UTF-8 name per path. Exceeding a geometry limit produces an explicitly partial map. Oversized HTTP responses and malformed JSON are errors; they never replace a valid cache. A complete, valid JSON response with a recognized timeout or out-of-memory remark may retain its geometry only when at least one nondegenerate segment intersects the requested area. That result is always flagged `partial` and reports the specific server reason. Empty, unknown-error, busy, rate-limit, or malformed responses keep the previous map. Geometry-count truncation also sets partial; a display of 256 paths is the local capacity, not proof of an Overpass error.

Version 1.1 keeps the version 1.0 cache object layout unchanged; old downloaded areas remain valid. Its actual street request is exercised through the shared production HTTP helper with only the ESP-IDF transport mocked. Recorded neutral Greenwich and Manhattan responses provide repeatable real-data parser checks; provenance records include source URLs, retrieval times, byte sizes, and SHA-256 hashes. The Manhattan 1.1 query was verified against the real server with HTTPS 200 and 88,865 response bytes. The revised center-first query was also checked with one neutral approximately 4 km by 4 km Manhattan request: HTTP 200, 225,690 bytes, 3.08 seconds, no server remark. Group counts were 1,119 central roads, 12,323 outer roads, and 300 scenery ways, with the same bounded output quotas. Those public test captures are separate from private user data.

The exact syntax follows the [Overpass JSON and geometry documentation](https://dev.overpass-api.de/overpass-doc/en/targets/formats.html) and the [output limit reference](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL#Print_(out)). The [HTTP interface](https://dev.overpass-api.de/command_line.html) supports percent-encoded GET queries. Cropped ways can include null gaps and coordinates just beyond the viewport. The parser splits gaps into separate paths and never joins them. It fills an area only when an entire retained ring has matching first/last points. The [cropped bounding-box documentation](https://dev.overpass-api.de/overpass-doc/en/full_data/bbox.html) explains these incomplete geometries.

This compact layer omits multipolygon relations and their holes, buildings, addresses, routing, and rich place POIs. Large parks or lakes represented only as relations can be absent. It is geographic context, not a complete or navigable street atlas. A successful empty response means no supported features in the requested area; it does not mean the download was missing. Cache storage has its own integrity checks and displays download time separately from current connectivity. Coordinates are software map positions and do not establish current GPS accuracy.

## Offline rights and attribution

OpenStreetMap data is distributed under ODbL 1.0 and can be copied and adapted with the required credit and license terms. Downloaded vectors may be retained on the SD card for offline use. Keep this credit visible on the map: **(c) OpenStreetMap contributors**. The app information screen and distributed cache/source documentation must identify **OpenStreetMap data: ODbL 1.0**, with `https://www.openstreetmap.org/copyright`. See the [OpenStreetMap copyright page](https://www.openstreetmap.org/copyright), [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/), and [OSMF attribution guidelines](https://osmfoundation.org/wiki/Licence/Attribution_Guidelines).

The standard OpenStreetMap tile service disallows offline prefetch/bulk download, so it is not used by this offline feature. That distinction is specified by the [OSMF tile usage policy](https://operations.osmfoundation.org/policies/tiles/). Cached data is never bundled as synthetic live content. Host-test fixtures are explicitly synthetic unless accompanied by a captured-response source record.
